1. Scope and Position
This document specifies how personal data enters, moves through, and leaves the platform. It closes three gaps from the register: erasure in vector stores (G1), data residency and subprocessors (G12), and agent memory governance (G15). They are treated together because they share one mechanism — the data map — and because an erasure request that misses memory or a cache is not an erasure.
Position in one sentence: the platform encrypts personal data per data subject, erases by destroying the key, and can prove it did so.

Why key destruction rather than deletion
Vector databases implement deletion as a metadata-level soft delete by design, to preserve index performance — the embedding remains physically unchanged on disk. Article 17 requires verifiable erasure rather than functional deletion, and an API returning no records is ambiguous between deletion and suppression. Under EDPB Guidelines 05/2019 erasure must be verifiable and irreversible and must extend to all storage layers including backup snapshots; cryptographic erasure was the only tested approach that eliminated recovery entirely.

Crypto-shredding design. Each data subject is assigned a data encryption key (DEK). All personal data and every derived artefact are encrypted under that DEK. The DEK is wrapped by a key-encryption key in the KMS. Erasure destroys the DEK, after which every ciphertext — including any in a backup taken months earlier — is unrecoverable. The audit artefact is the KMS key-destruction record, which is timestamped, signed and independently verifiable.
The consequence people miss: a backup restore does not resurrect an erased subject, because the restored ciphertext has no key. This is the property that makes backups compatible with Article 17, and it is the reason the mechanism is worth its complexity.

Erasure must span the primary store, embedding pipeline, caches and any derived knowledge graph, backed by an auditable deletion registry, with human review reserved for legal holds and backups. Cached summaries and pre-computed responses containing the deleted data must also be invalidated — this is the step most implementations omit.

Acceptance test — this is a release gate
Create a synthetic data subject. Exercise the full pipeline until the subject appears in vectors, cache, memory and logs. Issue an erasure request. Then attempt recovery from raw storage, from every cache, and from a backup taken before the request. Any recovered fragment fails the gate. Run this on every release that touches storage.

6. Residency and Subprocessors
Zero data retention is contractual and must be applied for, not assumed. Default abuse-monitoring log retention of up to 30 days is what trips most GDPR reviews. Apply for ZDR on every provider before EU traffic, and treat the absence of a ZDR arrangement as a blocker rather than a risk to accept.
Record six attributes separately per provider. A single "EU" claim conflates independent facts: storage location, processing location, retention period, training use, subprocessor list, governing jurisdiction. Maintain these in a table reviewed at each contract renewal, and note that vendor claims in this area have a short shelf life.

Residency is a routing constraint, not a configuration flag
AI vendors stack subprocessors faster than legacy SaaS; one documented case saw a major model provider become a productivity-suite subprocessor and fall explicitly outside EU Data Boundary scope for that route, surprising buyers who assumed the suite meant EU-only processing. For this platform the concrete exposure is the fallback chain: Component 2 can currently route an EU tenant to a non-EU provider during a failover. Tenant region must be a first-class routing input, and "no eligible in-region provider" must fail the request rather than silently crossing the boundary.

	•	Publish a subprocessor list with 30 days' notice before additions, and re-read every DPA on major vendor product changes rather than once at signature.
	•	Bind residency to the tenant record, not to a deployment, so a tenant migration is a data-movement event with its own approval.
	•	Test the boundary: a chaos test that fails all in-region providers must produce a refused request, not a cross-border call.
7. Agent Memory Governance
Safe deployment of persistent memory requires selective retention, secure storage, user-controlled deletion, and transparent auditing of what is remembered and forgotten — most production systems provide limited tooling for any of these.

Control
Requirement
Write policy
Scope-limited: an explicit allowlist of what may be persisted. Everything else is session-only.
Provenance
Every entry records origin and trust level at write time. Untrusted-origin entries are demoted at retrieval.
Source isolation
External content is never treated as equivalent to authenticated user input in a write decision.
Compaction filter
Trusted and untrusted content distinguished before summarisation, so payloads cannot survive into persistent memory.
Retention
12 months rolling, with high-relevance factual entries expiring on schedule rather than by decay alone.
User control
Users can view, correct and delete their own memory entries. This is the Art.16 and Art.17 surface.
Erasure
Memory is in the data map. Heuristics derived from a subject are derived personal data.

Two open problems to manage rather than solve. Cross-session identity resolution — the memory model assumes a stable user ID, which anonymous and multi-device sessions break — and staleness in high-relevance memories, where a confidently-retrieved fact becomes confidently wrong. Mitigate the second with contradiction checking on write and scheduled expiry; the first is a product decision about what anonymous sessions may persist, and the safe default is nothing.
Security note carried from the register: memory poisoning creates persistent compromise by decoupling injection from damage across sessions, which is why provenance is a data-protection control as well as a security one.
Retrieval should score entries by a weighted mix of recency, relevance and importance rather than embedding similarity alone, with provenance as a fourth term.
