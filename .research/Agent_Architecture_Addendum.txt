1. What This Addendum Corrects
The Implementation Plan and its companions specify infrastructure: gateway, storage, execution, safety, observability. They say almost nothing about agent architecture — how many agents there are, how they hand work to one another, what loop each runs, how tools and skills reach them, and whether the system learns from its own history.
That is a whole layer, and it sits between the infrastructure and the product. Six components are added below. One existing component — Model Fallback and Routing — is materially rewritten, because the plan treated routing as a failover mechanism when the current research treats it as a learned decision system with its own training data, benchmark and evaluation loop.

2. C18 — Routing as a Learned System
Version 2 specified "complexity-based routing with health checks and automatic failover." That is a failover mechanism with a heuristic in front. The research treats routing as a sequential decision process with five distinct components: context encoders, model encoders, scoring functions, decision rules, and learning signals, covering single-turn, multi-turn and personalised routing. Naming those five is useful because it tells you what you are actually building — and that four of the five do not exist in the current plan.

What routing is worth, and what it is not
Across 400,000 query–model instances spanning 21 datasets and 33 models, ensemble routing consistently beat every fixed single-model policy by approximately 7% in average accuracy — while a persistent ~19% relative gap to the Oracle remained. Both halves matter. Routing is a real and repeatable gain, and it is nowhere near the theoretical ceiling, so it should be budgeted as a continuous optimisation rather than a project that finishes.

2.1 Start with kNN
The counterintuitive finding: simple kNN matches or exceeds more complex learned routers, while offering large computational advantages — index construction for a million queries takes roughly 4.7 minutes at about 0.28ms per query, against roughly an order of magnitude more inference time for graph and attention-based routers. At thousands of routing decisions per second, that latency difference is the deciding factor.
Two related findings should shape the roadmap. Backbone embedding models have limited impact on routing quality, and larger model ensembles show diminishing returns compared with careful model curation. In other words: curate the model pool before tuning the router, and tune the router before changing the embedding model. That is the opposite of the order most teams work in.
2.2 The router needs its own data pipeline
This is the part the plan omits entirely. A learned router requires routing supervision — query, candidate model, observed quality, observed cost — which means a data generation pipeline and a held-out benchmark. Open infrastructure now exists for both: 16+ routers across single-round, multi-round, multimodal, agentic and personalised categories, with evaluation that replays pre-recorded executions of every benchmark query against all candidate models, so a local router sweep costs nothing to run once the executions are captured.
Adopt the replay design for your own traffic. Capture (query, model, response, quality score, cost, latency) for a sampled slice of production, then evaluate router candidates offline against that recording. This makes router changes as cheap to test as prompt changes, and it reuses the eval infrastructure in Component 14 rather than duplicating it.
The benchmark to model yours on spans generic LLM, memory-augmented, vision, time-series and personalised routing, and scores routers jointly on response quality and inference cost. Joint scoring is the point: a router evaluated on quality alone will always select the largest model.

Interaction with existing components
Routing memory — reusing previous query-to-model decisions — is a cache with a different key. It sits next to the semantic cache (C7) and inherits the same correctness risk: a stale routing decision sends a query to a model that has since been deprecated or has drifted. Give routing memory a TTL and invalidate it on any model version change, or C4's deprecation problem reappears through the side door.
3. C19 — Orchestration Topology
The first decision is whether to have more than one agent at all, and the honest default is no. Most teams adopt multi-agent before single-agent reaches its ceiling; each additional agent multiplies testing scenarios, edge cases and maintenance.

The cost multiple is large and frequently unmodelled
Multi-agent systems consume roughly 15× more tokens than chat interactions in production. Handoff-based swarm patterns generate 7+ API calls and 14,000+ tokens on multi-domain tasks, against about 5 calls and 9,000 tokens for sub-agent patterns with parallel support. Teams that select an architecture on capability alone without modelling per-run cost frequently discover 3–5× budget overruns. Given the 52% gross-margin environment established in the Gap Register, this is a margin decision, not only an architecture decision.

The production reality is narrower than the literature suggests: the overwhelming majority of deployments implement hub-and-spoke orchestrator-worker, not the swarm architectures that dominate academic papers. The guidance is explicit — avoid swarm in production, use hierarchy when decomposition is clear and graph when control flow is conditional.
Why swarm fails here specifically. Swarm obscures the execution path, making errors hard to trace when a chain of agents fails. This platform already has a detection problem — mean time to detect agent incidents measured in days, per the Gap Register — and a topology that hides the execution path makes that materially worse. Swarm is incompatible with the incident-response posture already committed to.
3.2 Escalation discipline
Adopt one rule and put it in the review checklist: start single-agent, measure where it caps out, and add the next pattern that addresses the measured failure mode. A topology change requires a named failure it resolves, a token-cost estimate on representative tasks, and an eval showing the improvement — the same bar as any other production change.
4. C20 — Execution Modes
"Plan mode, task mode, loop mode" map onto four established patterns with different cost and failure profiles. The plan currently assumes one implicit loop; it should make the mode an explicit, per-task-class configuration.

Mode
Mechanism
Choose when
Loop (ReAct)
Thought → action → observation → thought, until final answer
Next step genuinely depends on the last result. Exploratory, interactive work.
Plan-and-execute
Planner maps steps once on a strong model; executor runs them on a cheap one
Stable multi-step workflows with known dependencies. Plan is inspectable before execution.
ReWOO
Reasoning decoupled from observations to cut calls
Cost is the binding constraint on long chains.
Reflect (Reflexion)
Generate, critique, regenerate until the critic signs off or N rounds
Wrong final answers are expensive and a clear quality signal exists.

The cost arithmetic that should drive the default. Plan-and-execute costs roughly one strong-model call plus N cheap-model calls, which beats ReAct once N exceeds about three. Its failure mode is the brittle plan: the planner commits before seeing any tool output, so if step two returns something unanticipated, step three is already written and wrong. The fix is a re-plan gate — after every K steps, or on any step whose output falls below a confidence threshold, ask the planner whether to revise the remainder.
Selection discipline: start with ReAct and let observed failures dictate graduation — the other three patterns exist for specific failure modes that appear at scale: cost (ReWOO), complex planning (plan-and-execute), correctness (Reflexion).

Where loops actually break
Agent loops most commonly break at the perceive or observe step, not at reasoning. The three dominant production failure modes are runaway repetition, context degrading across iterations, and action taken on unverified output. The specific pathology worth instrumenting: the agent repeats a failed action sequence without verifying whether the expected state transition actually occurred, producing prolonged stagnation.

Required controls, all of which are missing from the current plan: a hard iteration ceiling per run, a no-progress detector that halts when N consecutive steps produce no state change, a per-run token and cost ceiling wired to the budget SLI, and mandatory post-action state verification before the next step is planned.
Observability consequence. Under the OpenTelemetry GenAI conventions already adopted in Component 15, plan-and-execute emits a distinct span shape — one planner span followed by N child agent spans. Instrument the mode as a span attribute so traces are comparable across modes and mode changes are visible in the trace history.
5. C21 — Tools, Skills and MCP
MCP standardises agent-to-tool connections while A2A handles agent-to-agent communication; both are now community-governed under the Agentic AI Foundation. The plan references neither. More importantly, it does not address the scaling problem that both create.

More tools make tool use worse
In measured tests, tool-selection accuracy fell from 43% to below 14% as tool count increased. The cause is architectural rather than a bug: MCP loads all tool descriptions in full at session start regardless of whether the conversation will use them, so the context cost scales with every tool added — and the context-rot effect established in Component 8 then degrades reasoning across the board.

The magnitude of the fix is unusually large. A reference task requiring roughly 150,000 input tokens with all tools preloaded dropped to about 2,000 tokens when definitions were loaded only on use — a 98.7% reduction on the same model with the same tools available. With over 10,000 enterprise MCP servers by April 2026, preloaded tool catalogues are the single largest source of wasted context.
5.1 Skills and tools are different primitives
A skill is a folder with a metadata header and a body of instructions, delivered by progressive disclosure: only name and description load at startup, and the body enters context once a request matches. An MCP tool is a callable capability whose schema is present in context. They solve different halves of the problem — packaged procedure versus live capability — and the platform needs both.

Use a skill when
Use an MCP tool when
The agent needs to know a procedure or house standard
The agent needs to read or write an external system
Content is knowledge-shaped and mostly static
Capability is live, bidirectional and stateful
It should cost nothing until relevant
Centralised OAuth, RBAC, telemetry and audit logging are required

MCP over HTTP remains the right choice for enterprise tooling platforms needing centralised OAuth, role-based access control, standardised telemetry and audit logging across many internal tools. That description matches this platform exactly, so the answer is not to abandon MCP but to stop preloading it.
5.2 Required architecture
	•	Progressive disclosure by default. Keep a lightweight index — tool names and one-line summaries — and load a full definition only when the model reaches for it. Tool-search mechanisms that load on demand above a context-share threshold are now available at the protocol level.
	•	Scope servers per task class, then filter individual tools with allowlists rather than exposing whole servers.
	•	Move heavy integrations to code execution. The agent writes code that calls tools through generated bindings, keeping intermediate results inside the execution environment instead of round-tripping every payload through context — which reuses the sandbox in Component 10 rather than adding infrastructure.
	•	Replace knowledge-shaped servers with skills. If a server exists mainly to deliver reference text, it is a skill wearing a protocol.
	•	Treat the tool catalogue as a governed surface. Tool count is now a quality metric, not a feature count — track it, and require a removal when one is added past the budget.
6. C22 — Recall and Retrieval Policy
The Gap Register resolved what memory stores and how it is secured. It did not resolve how memory is surfaced, which is a separate design with its own failure mode: retrieving the wrong memory is indistinguishable to the model from having no memory, and worse than none when the memory is stale.
Do not score recall on embedding similarity alone. The influential design scores memories by a weighted mix of recency (exponential decay), relevance (embedding similarity) and importance (a self-assessed score), which is a substantial improvement over pure cosine similarity. Add a fourth term this platform specifically needs: provenance, from the write-path tracking required by the memory-poisoning defences, so untrusted-origin entries are demoted at retrieval rather than only at write.
Staleness needs an explicit policy. Decay handles low-relevance memories; a high-relevance memory that has become false — the canonical case being a stored fact about a user's employer after they change jobs — is confidently retrieved and confidently wrong. Pair decay with contradiction checking on write, and expire high-relevance factual memories on a schedule rather than trusting decay alone.
7. C23 — Experience Store and Self-Improvement
Self-learning is achievable without touching model weights, and the reported gains are real: verbal self-reflection stored in memory produced 91% pass@1 on HumanEval against 80% without it. Prompt-level optimisation shows a similar picture, with reflective evolution reportedly outperforming reinforcement-learning baselines by around 10% using up to 35× fewer rollouts.
Two design findings worth adopting directly. First, distilled heuristics transfer better than raw trajectories — store the lesson, not the transcript. Second, the useful lesson depends on task type: failure-derived heuristics substantially outperform success-derived ones on search-shaped tasks (+14.3%), while success-derived heuristics work best on execution-shaped tasks (+9.0%). Retrieving from both is the reliable compromise when the task distribution is unknown.

Why this component ships gated, and last
The central risk of reflective memory is self-reinforcing error: an agent that wrongly concludes a call path always fails will avoid it permanently and never collect the evidence that would overturn the belief. Over-generalisation — a lesson learned in one context applied blindly in another — is the sibling risk, and the quality gates that would catch both (confidence scores, contradiction checking, periodic expiration) are described in the literature as necessary but still underdeveloped. A single bad reflection in a short-lived agent is contained. The same reflection in a persistent shared store propagates.

Required controls before enabling:
	•	Iteration limits, external verification, and diverse critic personas to prevent degeneration of thought and infinite loops.
	•	Memory hygiene as a first-class mechanism: versioned memories, scoring, and decay functions, or the buffer pollutes.
	•	Tenant-scoped by default. A heuristic learned from one tenant's traffic must not surface in another's. This is the same boundary as the vector store, and it is easier to breach here because heuristics look like generic knowledge.
	•	Human-reviewed promotion. Heuristics enter a candidate pool automatically and reach production only after review — self-improvement is a prompt-registry change (C13) and inherits its rollback SLO.
	•	Erasure-aware. A distilled heuristic derived from a data subject's interaction is derived personal data. It joins the G1 data map.
