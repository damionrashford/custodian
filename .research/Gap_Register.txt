1. Method and Honest Framing
"No more gaps" is not a reachable state, and a document claiming to have reached it would be misleading. A gap register is a living artefact: closing one gap routinely reveals two, and the standards that govern this platform — regulatory, model-provider, and accessibility — are all moving faster than any document can settle.
What this register does instead is audit the four existing documents against the categories a production platform is normally expected to cover, research the highest-severity gaps to the point where they can be acted on, and state plainly which gaps remain unresearched. A gap listed here as open is more useful than a gap silently omitted.

3. G1 — Right to Erasure in Vector Stores
This is the most serious gap in the set, and the least visible. The Implementation Plan specifies per-tenant namespaces and instant offboarding by namespace delete. That satisfies tenant separation. It does not satisfy an individual's erasure request, and the mechanism most vector databases use makes the problem worse than it appears.

The finding
Vector databases typically implement deletion as a metadata-level soft delete by design, to preserve index performance — the embedding remains physically unchanged on disk.  Article 17 requires verifiable erasure rather than functional deletion, and an API returning no records is ambiguous between deletion and suppression. Under EDPB Guidelines 05/2019 erasure must be verifiable and irreversible, and must extend to all storage layers including backup snapshots. In the reported tests, cryptographic erasure was the only approach that eliminated recovery entirely. 

Why the platform is exposed in three places at once. Deleting the vector is necessary but not sufficient. Cached summaries and pre-computed responses containing the deleted data must also be invalidated, which means the semantic cache (Component 7) and the context assembly memory (Component 8) are both in scope. Erasure must span the primary store, the embedding pipeline, caches, and any derived knowledge graph, backed by an auditable deletion registry.

Recommended position:
	•	Adopt crypto-shredding: encrypt per data subject, and erase by destroying the key. This is the mechanism that survives the soft-delete problem and produces auditable evidence.
	•	Maintain a data map from data subject to every derived artefact — vectors, cache entries, memory records, logs, backups — and document it in the DPIA under Art.35.
	•	Treat erasure as a durable workflow, not an API call. It spans systems, needs retries, needs an audit trail, and may need human review for legal holds. This is exactly the workload Component 9 exists to run.
	•	Add an erasure-completeness test to the definition of done: delete a synthetic subject, then attempt recovery from raw storage and from every cache.
Timing note: the EDPB launched its 2026 Coordinated Enforcement Action on 19 March 2026, with 25 national DPAs directly auditing transparency obligations. Deletion capability and processing transparency are being examined now, not prospectively.
4. G2 — SLOs and Error Budgets
No document currently states what "working" means numerically. Without that, the eval gate has no threshold to defend and the on-call engineer has no basis to decide whether an anomaly is an incident.
The core difficulty is that traditional SLOs assume a deterministic contract. Identical inputs can produce different but plausibly correct outputs, or quiet failures that never surface as errors. When an agent fails, the observability stack is frequently silent — HTTP 200, normal latency, zero error rate — while the agent approves something it should not have, writes to the wrong place, or loops through budget.

A reference bundle to calibrate against (from audits of 14 production deployments — treat as a starting point to be re-baselined on your own traffic, not as targets to adopt):

SLI

99.5% — provider APIs cap what is achievable above this
Latency
p95 < 3.5s non-streaming; < 800ms time-to-first-token streaming
Answer quality
≥ 0.85 LLM-as-judge on the production prompt mix, scored daily
Tool-call success
≥ 97% returning without retry exhaustion
Cost per resolved interaction
Set per use case; treated as an SLI, not a finance metric
Hallucination rate
≤ 1.5% on high-stakes prompts

	•	Run multiple error budgets in parallel, one per SLI. The accuracy budget can be healthy while the latency budget burns because a new model is slower.
	•	Measure before setting targets. Run for two weeks, take the baseline, and set the objective slightly above it. An agent completing 91% of tasks should not be given a 99% SLO.
	•	Tie autonomy to budget health. This is the mechanism that makes graduated autonomy operational rather than decorative: a clean 30-day record earns autonomy; a budget burning at multiples of the sustainable rate triggers escalation and demotion.
One finding worth internalising: across 14 models tested over 18 months of releases, accuracy improved steadily while reliability improved only modestly. Consistency is a separate objective from correctness and needs its own SLI.
5. G3 — Test Strategy
The Implementation Plan specifies an eval pipeline; the Engineering Standards specify domain-layer unit tests. Neither addresses the layer between them, which is where most agent defects live.
The framing shift required: conventional testing treats flakiness as a defect to eliminate. For agents, non-determinism is a property of the system under test and the framework must accommodate it as a first-class concern rather than suppress it. Practically, flaky AI tests usually indicate real non-determinism, prompt sensitivity, or model drift rather than broken test infrastructure.

Why single-run testing is misleading
Under the τ-bench unbiased pass^k estimator, one evaluated agent's success fell from pass₁ = 29.6% to pass₅ = 8.0% — only 8% of tasks succeeded on all five trials. The failures were also silent: no tool error marked a violating run.  A single passing run is therefore weak evidence that the agent complies with policy, and resampling is not a fix because in deployment the agent runs once.

Recommended structure — four tiers, each with a different gate:

Tier
Content
Gate
Deterministic
Schema, regex, JSON validity, tool-call shape. Milliseconds.
Blocking, every PR

Retrieval, prompt units, parsers in isolation against a golden set

Assert on properties rather than exact strings, average scores across three or more runs to absorb variance, and gate on thresholds rather than perfection. Deterministic checks run first so a five-millisecond assertion filters what would otherwise reach an expensive judge.
6. G4 — Model Deprecation
The plan pins model versions and mentions deprecation as an open question. The data says it needs to be a standing operational process rather than an open question.

The notice window is shorter than most migration plans
Across 208 tracked deprecation records from five providers, median notice is roughly 63–91 days depending on the provider, with observed ranges running as low as zero days. As of late August 2026, 29 of 53 scheduled retirements fell within the following 90 days.  Capacity should be planned around the worst case, not the median.

	•	Pin snapshots, never aliases. A rolling alias resolves to whatever the provider's current default is, so a call site using one cannot answer which side of a retirement date it sits on. This makes the prompt/config registry (Component 13) the model inventory as well.
	•	Run evals against the n+1 model continuously. The expensive failure is discovering on day 28 of a 60-day window that the replacement fails a material share of eval cases — the problem is not the failure rate but that it was unknown until the deadline.
	•	Expect silent regression, not errors. Repointing to a newer snapshot keeps returning 200s while tool-call formatting shifts, JSON adherence loosens, refusal boundaries move, and verbosity changes token budgets. Only the eval suite will catch this.
	•	Put retirement dates on the same calendar as certificate rotation and infrastructure renewals, with a named owner per call site.
	•	Negotiate notice into contracts. "Commercially reasonable notice" is not a commitment; a minimum notice period of 30–60 days for planned deprecations is.
7. G5 — Incident Response
No runbook exists in any document. For a system that takes autonomous action with real side effects, this is the gap most likely to convert a defect into a reportable event.

Detection is the failure point, not response
Mean time to detect across available agent-incident case studies is closer to 14 days than 4 hours, and the reason is structural: agents act in single transactions that look identical to authorised activity in the audit log.  Traditional software fails loudly; agents fail plausibly — the runtime is healthy, logs are moving, payloads are well-formed, and the work quality is dead. 

Required components, in build order:
	•	Detection panels first, kill switch second. A cost spike of 50× within an hour with no latency change is a detectable signature; so is a tool-call success collapse with a flat error rate.
	•	Rollback procedures per action class. Agent actions fall into classes with different reversal profiles — database writes, external API calls, payments, notifications, permission changes. Where rollback is impossible, the runbook must name the substitute: compensating action, customer notification, or regulatory disclosure.
	•	Blast-radius control precedes root cause. In the first five minutes the objective is containment, not diagnosis; if the incident followed a deploy, rollback is the default unless there is hard evidence it will not help, and cleanup is never combined with the rollback.
	•	Recover in tranches with verification between steps. An over-confident first recovery is among the most common causes of a repeat incident.
	•	Every incident becomes a regression test. This closes the loop into Component 14 and is the only mechanism that prevents the same failure returning in a new form.
Regulatory coupling (G6). Serious-incident reporting under EU AI Act Article 73 carries a short notification window, and current AI incident-response frameworks now include regulatory notification checkpoints at each phase. The runbook must therefore name who decides whether an incident is reportable, and within what internal deadline — a decision that cannot be made for the first time during an incident.
8. G7 — Certification Path
The situation is a genuine standards gap, and worth understanding before scoping the work. The AICPA has issued no authoritative AI-specific SOC 2 standard; auditors apply the 2017 Trust Services Criteria plus a practitioner-assembled AI overlay, increasingly tested against the OWASP LLM Top 10. Prompt injection is reportedly cited in nearly every 2026 SOC 2 audit evidence request.
Scope guidance: most AI companies selling to enterprise scope Security plus Confidentiality at minimum, add Availability when SLAs are contractual, and add Privacy whenever personal data is processed. ISO/IEC 42001 typically follows in year two or three, and becomes valuable when buyers are European or when building toward AI Act conformity.
The architectural consequence: AI in production expands SOC 2 scope to models, training data and automated decision-making, and expands evidentiary requirements to auditable records of production execution. That is the same audit trail required by Article 73 reporting, by Article 17 erasure evidence, and by AI Act deployer logging duties. Four separate obligations are satisfied by one well-designed execution log, which is the strongest available argument for building Foundation F3 properly in Phase 1 rather than iterating on it later.

All three are assessed at the 75th percentile of real page views over a rolling 28-day window, which means these are field metrics: a strong lab score is not evidence of conformance if a quarter of real visitors on mid-range devices see slow results. Product-specific risk. INP is the metric this platform is most likely to fail, because a streaming agent interface performs continuous DOM updates while the user is trying to interact. Budget for it explicitly: batch render updates, keep the main thread free during streaming, and measure INP  an active agent run rather than on an idle page.

One structural observation worth carrying forward. Four of the P0 gaps — erasure evidence (G1), incident reporting (G6), certification evidence (G7), and AI Act deployer logging — all resolve to the same underlying capability: a complete, queryable, tamper-evident record of what the agent did, with what data, on whose behalf. Foundation F3 in the Implementation Plan is currently one row in a table. It is in fact the single highest-leverage component in the entire programme, and it should be specified accordingly before Phase 1 begins.
