1. Purpose and Enforcement
This document defines the engineering standards for the autonomous agent platform. It is a companion to the Implementation Plan and applies to every component in it.
One governing principle: a rule without an automated check is a suggestion. Every standard below is stated with the mechanism that enforces it. Rules that cannot be enforced by the compiler, a linter, or CI are marked as review-time judgement and are deliberately few. Style debates are settled by the formatter, not in pull requests.
Standards apply to first-party source. Generated code, vendored dependencies, and migration scripts are exempt via explicit ignore paths, not by informal agreement.
2. TypeScript Configuration
Type safety is a build-gate, not an aspiration. A codebase where strict mode is technically enabled but routinely bypassed signals that type safety is aspirational rather than operational.
Baseline tsconfig.json — this is the floor, not a starting point for negotiation:

{
  "compilerOptions": {
    // Core strict family
    "strict": true,

    // Beyond-strict type safety
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noPropertyAccessFromIndexSignature": true,
    "noImplicitReturns": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "allowUnreachableCode": false,
    "allowUnusedLabels": false,

    // Module safety
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "moduleDetection": "force",
    "forceConsistentCasingInFileNames": true,
    "erasableSyntaxOnly": true,

    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "skipLibCheck": true
  }
}

Why these specific extras. noUncheckedIndexedAccess types an array index access as T | undefined, which catches off-by-one and empty-collection bugs that plain strict mode misses. exactOptionalPropertyTypes distinguishes a property being absent from a property explicitly set to undefined — the two are not equivalent and conflating them defeats runtime existence checks. erasableSyntaxOnly keeps the source compatible with native type-stripping runtimes.

Non-negotiable
Do not disable an individual strict flag to avoid fixing type errors — fix the errors.  Loosening the config to make a build pass is a rollback of the standard and requires the same review weight as a production change.

3. Type Discipline
Parse, do not validate. Untrusted input crosses the boundary once, through a schema parser, and everything downstream receives a fully-typed domain object. No function deeper than the boundary accepts a raw payload shape. This is the single highest-leverage rule in the document: it converts an entire class of runtime failure into a compile-time or boundary-time failure.
Make illegal states unrepresentable. Model state as a discriminated union rather than a bag of optional fields. A record with status plus four nullable columns admits combinations that cannot occur; a union does not.

// Rejected — admits { status: 'pending', result: 'x', error: 'y' }
interface Job { status: string; result?: string; error?: string; }

// Required — the compiler rejects impossible combinations
type Job =
  | { status: 'pending' }
  | { status: 'succeeded'; result: JobResult }
  | { status: 'failed'; error: JobError };

	•	Branded primitives at boundaries. TenantId, RequestHash, and PromptVersion are branded types, not bare strings. Cross-tenant leakage is the failure mode this prevents, and the plan's isolation guarantees depend on it.
	•	Exhaustiveness is checked, not assumed. Every switch over a union ends in a never default. Adding a variant must break the build in every place that handles it.
	•	Errors are typed and returned, not thrown, across module boundaries. Throwing is reserved for programmer error and truly unrecoverable conditions. Expected failures — provider timeout, guardrail rejection, budget exceeded — are values in the return type.
	•	No structural typing across trust boundaries. A type that happens to match is not the same as a type that was validated.
4. Separation of Powers
Four layers. Dependencies point inward only, and the rule is enforced by the linter rather than by convention.

Layer
Contains
May import
domain
Entities, value objects, business rules, port interfaces. Zero I/O.
Nothing. No framework, no SDK, no Node built-ins.
application
Use cases, orchestration, transaction boundaries.
domain only.
infrastructure
Adapters: provider SDKs, vector store, queue, Stripe, telemetry.
domain, application.
interface
HTTP handlers, workers, CLI, webhook receivers.
application, domain. Never infrastructure directly.

The load-bearing consequence: the domain layer must be testable with no network, no clock, and no environment variables. If a domain test needs a mock HTTP client, the dependency arrow is pointing the wrong way and the design is wrong — not the test.
Enforcement is eslint-plugin-boundaries (or import/no-restricted-paths) with the layer graph declared in config, plus dependency-cruiser in CI to fail on any cycle at any depth.

Applying this to the platform components
The Guardrails, Routing, and Context Assembly components each define a port in domain and an adapter in infrastructure. This is what makes the provider-swap and model-fallback requirements tractable: swapping a provider is a new adapter, not a change to business logic. It is also what makes the eval pipeline possible, because use cases can be exercised without a live provider.

7. Barrel Files — Restricted, Not Adopted
This section departs from the request, and the reasoning matters. Barrel files were treated as a best practice for years and have since been reassessed. The measured costs are concrete rather than stylistic.
Bundle and build cost. A library maintainer documented a Next.js dev page importing a single hook pulling a 552 kB client chunk that dropped to 64 kB once the barrel was removed — because dev mode does not tree-shake and the barrel entry compiled all 120+ modules including heavyweight transitive dependencies the page never referenced.
Correctness cost. Barrels are hotspots for circular dependencies, particularly when internal modules import through their own directory's barrel, producing runtime failures such as Cannot access 'X' before initialization that surface far from their cause. For a system with strict tenant isolation and durable workflow replay, non-deterministic module initialisation order is an unacceptable class of bug.
Developer-experience cost. Go-to-definition lands on the barrel rather than the source, identical index.ts tabs become indistinguishable, and the file itself becomes a recurring merge-conflict site.

Policy
One barrel per published module boundary. Zero barrels inside a module. Barrels belong at the edge of a unit that external code consumes, not scattered through internal folders.  If the project does not have the problem a barrel solves, do not add the pattern. 

	•	A barrel may exist only at a package root in the monorepo — the public API of @platform/guardrails, not of guardrails/internal/.
	•	Barrels must never re-export from another barrel. Nested chains are the direct cause of cycles.
	•	Barrels list explicit named exports. export * is banned — it makes the public surface unreviewable and unbounded.
	•	Type-only re-exports use export type so the barrel carries no runtime footprint.
	•	Internal code imports by direct path, always. Importing through your own module's barrel is the specific mistake that creates cycles.
Enforced by no-restricted-imports patterns plus a dependency-cruiser rule failing the build on any cycle.

Comments explain decisions the code cannot express. They do not narrate control flow, and they are not a changelog.

Test on every comment: if the comment could be deleted with no loss of information not recoverable from the code, delete it. If the code needs a comment to be followed at all, the code is the problem.
9. Dead Code, Deprecation, and Compatibility
Internal code: no deprecation tier. Within the repository there is exactly one way to do anything. When a better implementation lands, callers migrate in the same change and the old path is deleted — not marked deprecated, not left behind a flag. Two coexisting implementations mean the migration will not finish, and the second one becomes the one nobody tests.
	•	No commented-out code, no unreferenced exports, no orphan files. Enforced by knip or ts-prune failing CI on unused exports and files.
	•	No compatibility shims, adapter wrappers, or v2 suffixes for internal modules. Rename in place and fix the call sites.
	•	Feature flags carry a removal date and an owner at creation, and CI fails on flags past expiry.

Where "no backwards compatibility" must not apply
This rule stops at published boundaries. The platform emits webhooks to customer systems, exposes a tenant-facing API, and persists durable workflow state that outlives deployments. At those three boundaries, breaking a consumer is a production incident rather than a cleanup. The plan's own durable-execution requirement makes this concrete: a long-running workflow may replay under code deployed after it started, so old state must remain readable. The correct discipline is not backwards-compatible code but versioned contracts — version the webhook payload, version the API route, version the workflow definition, and retire old versions on a published schedule with consumer notice. Internal ruthlessness, external stability.
